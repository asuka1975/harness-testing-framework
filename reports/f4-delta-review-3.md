### 2.3 新しい手がかり

**(a) 並びの入れ替えが、同じ実行の組を映す（2 項目。人が読んでも分からない）。**

- labeling.py の `arrange` は、対象の中を人に見せる文の SHA-256 の順に並べ、そのうえで、全体の並びで同じ実行の項目が隣り合う所を入れ替える
- 試すと、二つのファイルで並びが SHA-256 の順から外れていた
  - 一つは、同じ対象の中の同じ実行の二項目のため
  - もう一つは、ファイルの最後の項目と次のファイル（ゲート）の最初の項目が同じ実行だったため。ファイルに分けた今は、別のファイルの項目が隣り合っても意味が無く、この入れ替えは要らない
- 外れ方から同じ実行の組が分かり、ワークフローの進み方を知っていれば、その組から 2 項目のクラスが推せる（付録 A.1）
- ただし、外れを見つけるには、labeling.py と同じ文を作って SHA-256 を計算する必要がある。それができる人はコーパスの印も読めるので、人が材料を読んで使える手がかりではない。前の確かめも、この入れ替えには触れていなかった（f78efe4 の一つのファイルでも同じ入れ替えがあった）
- 直すと番号が変わり、前の確かめの結果と比べにくくなる。記録だけでよい（E5-L5）

**(b) 途中で compare を走らせると、印が分かる（手順の手がかり）。**

- ファイルを一つずつ付ける形になったので、付け終えたファイルごとに `labels` と `compare` を走らせることができる（空の「ラベル:」は数えるだけ）
- compare は、食い違った項目の印を出し、混同行列でクラスごとの数を出す。たとえば、前のフェーズのゲートの項目で食い違いが出れば、後のゲートの項目の付け方に響く
- 00-guide.md の「付けた後」は「付け終えたら、…次を実行する」とだけ書く。ファイルごとの付け方と並んでいるので、「付け終えたら」がファイルごとか全部かが読み分けにくい（E5-L3）
- `labels` だけなら印は出ない（数、空、誤りの番号と選べる選択肢だけ）。途中で書き方を確かめるのには使える

### 2.4 設計で扱う性質（前の確かめの E4-M2）は、今も同じ

- 項目の中身が前と同じなので、後の対象とゲートから前の対象が推せる性質も前と同じである。今の形では、それは後のファイルを開いた時にだけ使える。前のファイルを付け終えてラベルを変えないという頼みを、人が守れば効かない
- README の「残る手がかり」の (1)〜(3)（設計を知る人には完全な盲検でないこと、同じファイルの中の訪問をまたぐ同じ文、頼みを強いる手段が無いこと）は、事実と合う
- README の「分けた理由」の「ワークフローは goal でだけ次へ進み」には、一つ例外がある。運用者の goal 到達扱いの続行（`ContinueAsGoal`）で非 goal の成果物が下流に流れるシナリオの項目が、材料に一つある。前の確かめで指摘済みの例外で、推し方を不確かにするだけである。手引きの同じ文と合わせて、低とした（E5-L6、B5-L2）

### 3.1 読み方（00-guide.md）は事実だけで足りるか（盲検のエージェントのラベル）

**方法。**

- 複製の材料から、10 の写しを作った。各写しは、00-guide.md と、一つの対象のファイルだけで、どちらも材料のまま（変えていない）

- 写しを、この会話の文脈を持たない別々のサブエージェント（同じモデル）に渡した。指示は「二つのファイルだけを読む。ほかのファイルは開かず、コマンドを実行しない。00-guide.md の読み方に従い、各項目の選べる選択肢の id を一つ選び、確信と理由を一行で返す。読み方の説明で困った点を五つまで挙げる」だけ。前の確かめと同じ形で、材料にない指示は足していない
- 返ってきたラベルを、複製の材料の「ラベル:」に「ラベル: <id>（盲検、確信 <高中>）」の形で書き、書かれた手順（`labels`、`compare`）で印と比べた
- 留保
  - これはエージェントのラベルで、人手のラベルではない
  - ラベラーは私と同じ系統のモデルで、人と違う偏りを持ちうる
  - 一つの写しに一つの対象しか無いので、ファイルの順に付ける時の体験（前のファイルの記憶）は写していない

**結果。**

- `compare`: ラベル 66 件、κ 0.981、一致率 0.985、食い違い 1 件
  - 前の確かめ（方針の二つを材料に入れていた時）と同じ値で、同じ項目が食い違った（付録 A.3）
  - 確信は「高」41、「中」25。前は、66 項目のうち 28 項目が「中」か「低」だった
- 前に方針がラベルを決めていた所（ゲートの記述の括弧の列挙、記憶の列挙の中身を確かめるか）は、今回も同じラベルになった。ただし、ラベラーはそれを「困った点」に挙げ、確信を「中」にした。方針を外したことで、記述の曖昧さが確信と理由に現れるようになった。手引き第15.1節の目的（記述の問題を見つける）に合う

**ラベラーが困った点。** 10 人のうち複数が挙げたものを並べる。

1. **置き書きを空と数える決まり（4 人）。** 「（判断できない）」は「無い」ではなく「判断を放棄した」の意味なのに、空と数えてよいか。一つの項目では、この決まりで選ぶ選択肢が変わりうる所まで来た（ラベラーは確信を「中」にした。付録 A.2）。ほかの 3 人は「結果は変わらなかったが、意味の違いが消える」と書いた（E5-L1）

4. **要件の根拠を推論で認めるか（2 人）。** 「エラー」を ValueError と読む、百分率の下限 1、REQ-4。前と同じ
5. **記憶や review.json に列挙された問い、食い違い、指摘が本当かまで確かめるか（4 人）**
