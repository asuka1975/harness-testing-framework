## 2. 分布基準の設定（必須項目）

### 2.1 設計値からの導出

stochastic.yaml の markov の設計値と workflow.yaml の遷移規則（戻りの辺と max、unknown と max 超過は中止、ゲートは toy では常に goal）だけを使い、フレームワークを使わない列挙で、実行の道筋 976 本（確率の和 1）を数え上げた。各基準について、条件に合う評価の数の期待値 E[n] と、割合の設計値を求めた。

| 基準 | 設計値（導出） | ファイルの注記 | E[n]（N=200） | SE | 幅 [min, max] | 下側 / 上側の幅（SE の何倍か） |
| --- | --- | --- | --- | --- | --- | --- |
| ask_topic 訪問 1 = unknown | 0.0500 | 0.05 | 200.0 | 0.0154 | [0.0, 0.12] | 3.24（0 で切る） / 4.54 |
| plan_outline 訪問 1 = topic_unclear | 0.2500 | 0.25 | 190.0 | 0.0314 | [0.15, 0.35] | 3.18 / 3.18 |
| write_note 訪問 1 = goal | 0.8000 | 0.80 | 175.5 | 0.0302 | [0.70, 0.90] | 3.31 / 3.31 |
| review_note 訪問 1 = findings_blocking | 0.3000 | 0.30 | 162.8 | 0.0359 | [0.20, 0.40] | 2.78 / 2.78 |
| review_note 訪問 2 以降 = findings_blocking | 0.1000 | 0.10 | 50.0 | 0.0424 | [0.0, 0.22] | 2.36（0 で切る） / 2.83 |

- 設計値はすべて、ファイルの注記と一致する。toy の偽の本体はクラスの分布が (ステージ, 訪問の区分) だけで決まり、ゲートは常に goal で、指標と印の組み合わせが変種のクラスと食い違わない（各フィクスチャで確かめた）。だから割合は、比の推定量でも設計値に収束する
- 実際のランタイムを 20000 回走らせて、(ステージ, 訪問 1 / 2 以上) ごとの経験分布を設計値と比べた。最大で |z| = 2.3（約 30 個の値の中で）。本体は設計どおりの分布を出している
- 「標準誤差のおよそ 3 倍」（D-8）は、分母を N ではなく E[n] にとれば概ね成り立つ。ただし ask_topic の上側は 4.5 倍と広く、review_note の二つは 2.8 倍と少し狭い（L1）
- 「訪問 2 以降」の基準は分母が 50 前後しかない。Wilson の区間の幅は 0.19 前後で、基準の幅 0.22 とほぼ同じになる。D-8 の「区間が基準の幅より広ければ回数が足りない」の境目にある

### 2.2 幅は既定の回数に対して妥当か

設計値とワークフロー規則だけで作った独立な模型でモンテカルロを行い、実際のランタイムでも確かめた。

| N | 正しい基準のどれかが落ちる確率（模型） | 同（実際のランタイム） | ずらした基準のどれかが通る確率（模型 / 実際） |
| --- | --- | --- | --- |
| 1000 | 0.000（2000 回の試行） | — | 0.000 / — |
| 200（既定） | 0.012（20000 回の試行。基準ごとに 0.0001, 0.0021, 0.0007, 0.0052, 0.0042） | 3/400 = 0.0075 | 0.0001 / 0/400 |
| 100 | 0.111 | — | 0.004 / — |
| 50 | 0.393 | 67/200 = 0.335 | 0.057 / 13/200 = 0.065 |
| 20 | 0.705 | — | 0.281 / — |

- 既定の N=200 では幅は妥当。種を固定しているので、テストは揺れない（種 10000 では通る）。種を変えても 1% 前後でしか落ちない
- 正しい基準が 95% の確率で落ちる真の割合（正規近似）は、ask_topic の unknown で 0.163 以上、plan_outline で 0.409 以上か 0.112 以下、write_note で 0.932 以上か 0.640 以下、review_note 訪問 1 で 0.465 以上か 0.153 以下、訪問 2 以降で 0.330 以上。N=200 で検出できるのはこの程度の大きなずれまで、ということ。分布テストの検出力の限界として、利用者に示すとよい
- **既定より小さい N では、この幅は使えない（M2）。** 幅は N=200 から決めてあるのに、`HTF_RUNS` は N を変えても幅を変えない。`runs_from_environment` の docstring は「CI では小さく」と書いている。D-7 の「既定を小さくし、環境変数で増やせるようにする」とも食い違う。N=50 だと正しい基準の 3 割以上が落ち、ずらした基準の 6% が通る。手元では、種 20000 なら N=20・50・100 のどれでも正しい基準が落ちた。種 10000 では偶然に通る（`HTF_RUNS=20` で toy のテストを走らせても通った）。N=20 の時の「訪問 2 以降」の基準は、条件に合う評価が 5〜6 件しかないのに、0/6 で通っていた

### 2.3 ずらした基準は「ずれている」と言えるか

- ずらした五つの幅の下端は、どれも設計値から 4.0〜9.7 SE 離れている（ask_topic 9.7、plan_outline 6.4、write_note 4.0、review_note 訪問 1 4.2、訪問 2 以降 4.7）。正しい幅とは重ならない。ずれていると言える。N=200 で 400 通りの種を試し、どれか一つでも通ったことは一度も無い
- ただし五つとも上にずらしてあり、正しい幅のすぐ外側にある基準（境目の近く）や、下にずらした基準は無い（L2）。判定の端そのもの（min と max を含む）は、合成の実行で tests/test_distribution.py が確かめている

### 2.4 判定の規則（D-8）は計画書の意図に合うか

- 計画書 第2節の例「N 回実行して goal 到達 80% 以上」は、観測した割合への閾値と読むのが字義どおり。点推定を [min, max] で判定する D-8 の規則は、この読みに合う。toy の基準は、設計値の周りの両側の幅として使っており、ずらした基準を落とす目的にも合う
- 足りない点（M2）: 判定は回数の不足を検知しない。条件に合う評価が 0 件の時だけ「判定できない」になり、1 件でも通りうる。Wilson の区間は報告に添えるだけで判定には使わない。そのことは adopting.md 第12節に書いてあるが、閾値（例: 80% 以上）から幅を決める方法と、幅と N の関係は書いていない。実ハーネスで真の割合がちょうど 0.80 なら、min: 0.80 の基準は約半分の確率で落ちる。これを人が知る手段は報告の区間だけ
- Wilson の区間の実装は正しい（第4節）

### 2.5 種による揺れ

種の基点を 20 通り（10000〜200000）変えて、N=200 の観測値を見た。ask_topic の unknown は 0.030〜0.075、plan_outline は 0.205〜0.302、write_note は 0.746〜0.844、review_note 訪問 1 は 0.240〜0.368、訪問 2 以降は 0.057〜0.172（分母 40〜67）。20 通りすべてで、正しい基準は通り、ずらした基準はすべて落ちた。種の基点を 400 通りに増やした結果は 2.2 の表にある。

## 3. オラクル検証（必須項目）

### 3.1 期待値の計算し直し

tests/test_oracle.py の配分（真のクラスごとの件数 goal 50、x 30、unknown 20 と、各行の周期）から、混同行列を組み立て直した。

- 混同行列: goal→goal 45, goal→x 5, x→x 24, x→goal 6, unknown→unknown 16, unknown→goal 4
- κ: p_o = 0.85。分類器の側の周辺度数は goal 55、x 29、unknown 16 なので、p_e = (50·55 + 30·29 + 20·16) / 100² = 0.394。κ = (0.85 − 0.394) / 0.606 = 0.752475。scikit-learn の `cohen_kappa_score` も 0.7524752475、実装も同じ値
- ECE: 確信度 0.9 の 45 件（全問正解、差 0.1）、0.8 の 24 件（差 0.2）、0.7 の 16 件（差 0.3）、0.6 の 15 件（全問不正解、差 0.6）。ECE = 0.45·0.1 + 0.24·0.2 + 0.16·0.3 + 0.15·0.6 = 0.231。区間を左閉じにしても右閉じにしても同じ値（各確信度が別の区間に入るため）
- 再実行の一致率: FlakyClassifier（every=4）は、初めて見た順の 0, 4, 8, … 番目の 25 件だけ二回目以降の答えを変える。一致率は 75/100 = 0.75。reruns=3 でも 0.75 になる（実測も同じ）
- toy の test_oracle（MarkerClassifier で確信度 0.9、印を正解とする）: 全問正解なので κ = 1、ECE = |1 − 0.9| = 0.1。期待値は正しい

### 3.2 実装は標準の定義どおりか

- `cohen_kappa`: (p_o − p_e) / (1 − p_e)。p_e は二人の周辺度数の積の和で、標準の定義どおり。答え無し（None）は分類器の側だけの独立のカテゴリで、ラベルとは一致しないので p_e には寄与しない。p_e = 1 の時は、一致が完全なら 1、そうでなければ 0 を返す（よく使われる慣例）。項目が 0 件だと ZeroDivisionError（L10）
- `expected_calibration_error`: 区間ごとの |正解率 − 平均の確信度| を件数で重みづけた和で、標準の定義どおり。小数第 1〜6 位の確信度をもつ乱数の組 2000 通りで、独立に書いた参照実装（左閉じ）との差は最大 1.7e-16
- `oracle_report`: κ と ECE は一回目の結果から計算する。再実行の一致率は「reruns 回すべて同じ選択」の割合。docstring と D-8 のとおり
- 状態文書の SHA-256 が実行記録にあり、置き場から読めることを、toy の実行で確かめた（D-7）

### 3.3 区間の端の扱い

- 実装は [i/10, (i+1)/10) の左閉じで、最後の区間だけ 1 を含む（D-8 の記述どおり）。Guo ら（2017）の ECE は右閉じ ((i−1)/M, i/M] で定義されている。0.6・0.7・0.8・0.9 のように区間の境目ちょうどの確信度は、LLM が申告する確信度でよく出る。小数第 1 位までの確信度の乱数の組では、2000 組のうち 271 組で両者の ECE が違った。どちらも使われている慣例なので誤りではないが、adopting.md 第15節には書いていない（L5）
- `int(round(c * 10, 9))` なので、境目より 5e-10 以内だけ小さい値は上の区間に入る（0.5999999999 は区間 5、0.59999999999 は区間 6）。実害は無いが、意味は文書に書いておくとよい
- 区間を一つずらす変異、右閉じにする変異、区間数で単純平均する変異は、どれも test_known_ece_with_ten_equal_width_bins で落ちる（第6節）

### 3.4 答え無しの扱い（M4）

- D-8 は「答え無しは独立のカテゴリとして数え、確信度 0 の不正解として較正に入れる」と決めている。実装もそのとおり
- この規則では、答え無しは較正の上では「完全に較正されている」（確信度 0、正解率 0）ことになり、ECE に 0 を足して分母だけを増やす。答え無しが多い分類器ほど ECE が下がる。例: 20 件で ECE 0.30 の組に答え無しを 20 件足すと、ECE は 0.15 になる。閾値は較正の結果から決める（第2節の固定判断）ので、この希釈は閾値の判断を誤らせうる
- この規則を確かめるテストが無い。答え無しを較正から除く変異が生き残った（第6節の M5）。test_unanswered_is_its_own_category は混同行列と件数だけを見ている

### 3.5 範囲外の確信度と分類器の例外（M3）

契約 2.2 の 3 と D-6 は、分類器の例外と、0〜1 の有限の数でない確信度を「答え無し」とする。ランタイム（runtime/oracle.py）はそのとおり正規化しているが、`oracle_report` は分類器の答えをそのまま使う。

- 確信度 −0.3 で goal を答える偽の分類器は、答え無しに数えられず、Python の負の添字で区間 [0.7, 0.8) に入り、ECE が 1.3 になる（1 を超える）
- 確信度 1.5 は最後の区間に入る。NaN は ValueError で止まり、分類器の例外もそのまま外へ出る
- 同じ分類器が、ランタイムでは unknown、オラクルのレポートでは別の扱いになる。オラクル検証は高リスクの検証（第5.7節）なので、契約と同じ正規化に揃えるべき

## 5. 独立性検証: 検出すべきものを検出し、誤検出しないか

### 5.1 玩具以外の設定（合成の実行、alpha 0.01）

帰無仮説の下（代表どうしで下流の分布が同じ。分布は goal 0.6、x 0.3、unknown 0.1）。300 回の試行での誤検出率:

| 代表の数 | 代表ごとの件数 10 | 30 | 100 |
| --- | --- | --- | --- |
| 2 | 0.000 | 0.007 | 0.003 |
| 3 | 0.017 | 0.007 | 0.003 |
| 5 | 0.007 | 0.007 | 0.007 |

件数が不揃い（10 と 200）なら 0.007、稀な結果（0.97 / 0.03、30 件ずつ）なら 0.000。並べ替え検定なので、どの設定でも名目の水準を保つ（300 回の試行の誤差の範囲）。

対立仮説の下での検出率（200 回の試行）:

| 下流の違い | 代表ごとの件数 20 | 50 | 100 | 200 |
| --- | --- | --- | --- | --- |
| 0.30 対 0.40 | 0.015 | 0.04 | 0.07 | 0.27 |
| 0.30 対 0.45 | 0.035 | 0.15 | 0.29 | 0.65 |
| 0.30 対 0.60 | 0.20 | 0.60 | 0.91 | 1.00 |

代表が 5 つで一つだけ 0.3 から 0.6 にずれている場合、50 件ずつで 0.72。toy の divergent に当たる違い（0.10 対 0.60）なら、20 件ずつで 0.72。toy の divergent の違いは非常に大きく、300 回の実行（代表ごとに約 170 件）なら確実に検出できる。違いが 0.15 程度なら、代表ごとに数百件が要る。判定 `independent` は「この件数では違いを検出しなかった」という意味で、「揃っている」とは言えない（L13）。

### 5.2 構造上の見落とし: フェーズの最終ステージの goal（H1）

遷移の「次の状態」は、同じ実行の中の次の評価である。フェーズの最終ステージが goal なら、次の評価はいつもそのフェーズのゲートの評価になる。ゲートがほぼ goal なら、次の状態はほぼ一つの値しかとらず、次のフェーズの最初のステージの分布が代表によって違っても見えない。

複製の上で、偽の本体を書いて確かめた。plan_outline（intake の最終ステージ）に goal の変種を二つ置き、write_note の分布が outline.md の中身で大きく変わるようにした。600 回の実行で、二つの代表のあとの write_note の goal は 72/322 と 303/355 に分かれた。それでも独立性検証は `stage:plan_outline=goal: independent p=1.0` を返した。次の状態がすべて `phase:intake=goal` だったため。

この見落としは件数を増やしても消えない。計画書 第2節の固定判断（クラスの粒度は独立性検証の結果でのみ変える）が、フェーズの最終ステージの goal には働かない。F4 の software factory は 4 フェーズ以上なので、「仕込んだ粗いクラスの検出」をフェーズの最終ステージに置くと検出できない。

### 5.3 訪問の区分による誤検出（M1）

マルコフ合成（D-8）は、クラスの分布が (ステージ, 訪問の区分) で決まると仮定する。独立性検証は、状態を (ステージ, 結果) で作り、訪問で層別しない。再進入で成果物が変わり（carry を受けた書き直しでは自然に起きる）、下流の分布が下流自身の訪問で変わる（toy の stochastic.yaml の first と again がまさにそれ）と、クラスは正しくても代表と下流の訪問が結びつき、違反と判定される。

複製の上で、markov の write_note だけを「訪問 1 は ok、訪問 2 以降は ok_b」に変えた設定（confound）を作った。

- 独立性検証: `stage:write_note=goal: violated p=0.0005`（300 回でも 1000 回でも）
- 同じ設定でマルコフ合成の予測と実測を比べると（推定 2000 回、実測 2000 回）、17 個の量すべてが一致した

D-8 のモデルの下では正しいクラスなのに、二つのランナーの判定が食い違う。toy の markov では二つの代表が訪問 1 と訪問 2 以降に同じ割合（0.4 / 0.4 と 0.45 / 0.45）で出るので、この食い違いは表に出ていない。

### 5.4 その他

- 代表は、ステージが書いた成果物の内容のハッシュ（D-8）。偽の本体のようにフィクスチャを写すなら数十件の同じ代表が集まるが、実際の LLM の出力はほぼ毎回違うので、代表ごとに 1 件しか集まらず、いつも undetermined になる。実ハーネスで使うには、代表の鍵をハーネスが与える口が要る（L8。F3 の範囲外だが、F5 の雛形の「独立性」の手順までに要る）
- 複数の状態をそれぞれ alpha 0.01 で検定しており、多重性の補正は無い。toy では検定できる状態が一つだけなので影響は無い（L8）

## 7. 汎用性の規律（第5.8節）

- src/ に、玩具のステージ名（ask_topic、plan_outline、write_note、review_note）、成果物名（note.md、topic.txt、outline.md、brief.txt）、玩具の文言（議事録、抽象的）、特定の LLM やツールの名前は無い（grep）。玩具の前提（ゲートが常に goal、変種の名前）も本体に無い
- 印 `[[class <対象>=<クラス>]]` は、フレームワークの偽物（MarkerClassifier、ConfusionClassifier）の決まりで、玩具に固有のものではない。ただし oracle が harness.fakes の非公開名 `_MARKER` を import している（L10）

- ECE = (45·0.1 + 16·0.3 + 9·0.6) / 70 = 14.7 / 70 = 0.21。答えた割合は 0.7。実装は 0.21 と 0.7 を返し、numpy で書いた左閉じの参照実装も 0.21 を返した
- κ（答え無しを独立のカテゴリとして数える）: p_o = 0.61。分類器の側の周辺度数は goal 49、x 5、unknown 16、答え無し 30 なので、p_e = (50·49 + 30·5 + 20·16) / 100² = 0.292。κ = (0.61 − 0.292) / 0.708 = 0.4492。実装の値と一致
- 答え無しを入れない ECE は、答え無しが多くても値が下がらない（2.5）。閾値の判断に答えた割合を併せて見る形は、計画書の「閾値は較正結果から決める」に合う
- 前回の既知の κ（0.7525）、ECE（0.231）、再実行の一致率（0.75）のテストは、そのまま通る
