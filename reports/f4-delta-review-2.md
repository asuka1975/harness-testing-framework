**方法。**

- 複製の材料から、写しを六つ作った
  - 冒頭（読み方、見せ方、ラベルの書き方）は、そのまま残した。ただし E4-M1 の括弧書き「（ゲートは goal）」だけは除いた（ゲートの記述を印なしで確かめるため）

- 返ってきたラベルを、複製の材料の「ラベル:」に「ラベル: <id>（盲検、確信 <高中低>）」の形で書き、`labels` と `compare` を走らせた

  - これはエージェントのラベルで、人手のラベルではない
  - 写しは E4-M2 の手がかりを分け、E4-M1 の括弧書きを除いた。人に渡す材料そのままではない
  - ラベラーは私と同じ系統のモデルで、人と違う偏りを持ちうる

  - ゲートの訪問 2 以降の項目では、ラベラーが理由に、方針の「括弧の中の列挙は、記述が書いた範囲」を挙げた
  - acceptance の推論に基づく食い違いの代表では、ラベラーが記述の優先の文で選んだ。ただし、食い違いが本当かを確かめるべきかで迷ったと書いた（確信 中）
  - どちらも、方針がラベルを決めている。B4-M1 を参照
- 食い違った 1 項目の理由は、方針と事実のどちらにも無い点（下の (1)）だった

**ラベラーが共通して困った点。** 六つの写しのうち、複数で挙がったものを並べる。

1. 保留の返事（「未定」「そのうち考えるよ」「来月の末に決める」）を、「回答がある」と数えるか。また、それが「## 未決事項」（なし）と食い違うか（intake、analyze、ゲート、acceptance の訪問 2 以降と、持ち帰りありの項目。四つの写しで挙がった）
2. 「（判断できない）」「（実行できなかった）」が、空として数える「（なし）など」に入るか。事実の文は「（なし）」しか例に挙げない（三つの写し）
3. 記述が中身の条件を書いているかの境目。たとえば、acceptance の goal の「表がすべて合格」は表の文の条件か、中身を確かめる条件か。主経路の実装の REQ-1 の欠陥（支払額の切り捨て）に、四つの写しのラベラーが気づいた（acceptance、unit\_test、implement）
4. 記憶に列挙された問いや食い違いの中身の正しさまで確かめるか（acceptance の推論の食い違い、plan\_tasks の design\_issues、implement の task\_questions）
5. 状態文書にテストの実行結果が無いこと。テストが通るかは、頭の中で走らせて決めるしかない（unit\_test、implement）。事実の文は「指標の値は入っていない」とだけ書く
6. 記述そのものの曖昧さ
   - 要件の根拠に、回答から導いた値（REQ-4、ValueError、百分率の下限 1）を含めるか
   - implement の goal の「design.md の構成どおり」は「## 構成」の節だけか（design.md の「## 対応」は REQ-1 を「割引額を切り捨ててから引く」とし、主経路の実装はそれと違う）
   - plan\_tasks の goal の「paths が重ならない」に tests が入るか
   - requirement\_unmet の「依頼と食い違っていない」の「依頼」に、intake.md の回答が入るか

(2) と (5) は事実なので、材料に書き足せる（E4-L3）。(1)、(3)、(4) は読み方の方針で、人間が決める（B4-M1、第9節）。(6) は記述の問題で、記録だけにする（記述を直すには人間の承認が要る）。

### 4.2 共通の区切りを戻すと、分類器が見た状態文書に戻るか

- 材料の文だけから各項目の状態文書を組み立て直した。「（共通）」の付いた見出しの行を、節の頭の同じ見出しの区切りの全文に置き換えた（自前のスクリプト）
- 66 項目すべてで、組み立て直した文は labeling.py の人に見せる状態文書（`shown_state`）と同じだった
- コーパスの状態文書を `unmarked` したものと比べると、違いは次の二つだけで、ほかの行はすべて同じだった
  - 印だけの行（印を除くと空か「#」だけになる行）が無い
  - 区切りの間の空行が一つにまとまっている
- 落ちた印だけの行は、どれも成果物の頭の注釈で、クラスによらず同じ位置にある。印を含む行で中身が残るのは、review.json の一行だけ（`"marker": ""`）
- よって、共通の区切りを戻すと、分類器が見た状態文書から印と印だけの行を除いたものに戻る。材料の「事実」の説明（印を除いたもの。印だけの行は落としてある）と合う

## 9. 人間がラベルを付ける前に知っておくべきこと（印には触れない）

1. **材料には、まだ印が推せる手がかりが二つある（E4-M1、E4-M2）。直してから付けるのがよい。**
   - 直さずに付けるなら、次を守る
     - 「ラベルの書き方と、付けた後」の 2 の括弧書きを読まない（先に消してもらう）
     - 対象の節の順に付け、後の節を読んだ後に前の節のラベルを変えない
     - 項目どうしや節どうしを見比べず、各項目をその状態文書と選択肢の記述だけで選ぶ
   - 付け終えるまで読まないもの: README の「記述と代表の整合」、材料の冒頭が指す adopting.md 第15.1節、この報告の第3節・第4.1節・第5節・第10節・付録、前の報告（f4-delta-review.md）の第4.1節と付録
2. **読み方の方針の一部は、まだ人間が決めていない（B4-M1）。** 材料の方針のうち、次の二つは記述の読み方を決める。前の確かめで、人間が決める事項とされた
   - 記述が中身の条件を書いている時だけ中身を確かめる
   - 括弧の中の列挙は記述が書いた範囲として読む
   この二つは分類器（LLM）には渡らない。方針によってラベルが変わる項目がある。付ける前に、方針を採るか決めておく
3. **方針と事実で決まらず、ラベルが割れうる点がある（第4.1節）。** 迷ったら材料のとおり unknown と理由を書けば、後で記述か代表の問題として拾える
   - 保留の返事（「未定」「そのうち考える」）を回答と数えるか
   - 「（判断できない）」「（実行できなかった）」を空と数えるか
   - 回答から導いた値（REQ-4、ValueError、百分率の下限）を要件の根拠と数えるか
   - 記憶に列挙された問いや食い違いが本当かまで確かめるか
   - 状態文書にテストの実行結果は無い
4. **主経路の実装は REQ-1 に反する（D-17 の 5 で承認）。** 盲検のラベラーは、acceptance、unit\_test、implement の項目でこれに気づいた。implement の goal の記述（「design.md の構成どおり」）は、design.md の「## 対応」の REQ-1 の書き方と実装が違う点にも触れうる。記述がそれを判断の条件にしているかで、ラベルが変わりうる
5. **分量。** 66 項目、約 10 万字。各対象の節の頭に、選択肢の記述と、項目の過半で同じ区切りが一度だけある。項目の状態文書の「（共通）」の区切りは、節の頭のものと同じである
6. **付け終えたら**、examples/software-factory/ で次の二つを実行する
   - `uv run python -m software_factory.labeling labels --labeler <名前>`
   - `uv run python -m software_factory.labeling compare`

   書き方の注意
   - ラベルは「ラベル:」と同じ行に一つだけ書く。全角のコロンでもよい
   - 一行に id を二つ書かない（最初の id が黙って採られる。E4-L1）
   - `labels` は、読めないラベルを番号つきで挙げて止まる
   - `write` は埋めたラベルを消すので、実行しない
7. **完全な盲検ではない。** 人間は、記述と代表の設計（D-17 の回答など）を知っている。その知識は材料の外にあり、材料の直しでは除けない
