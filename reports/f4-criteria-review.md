## 1. 確かめ方

### 1.1 設計値からの独立な導出

workflow.yaml と tests/stochastic.yaml だけを読む模型を自分で書いた。遷移の規則は次のとおり。

- ステージの訪問の番号は、ステージごとに数え、戻しても戻らない。区分は訪問 1 なら first、2 以降なら again。release は carry の有無で分布を選ぶが、release に戻る辺は自分自身への notes_incomplete だけなので、訪問 2 以降と一致する
- goal なら次のステージに進む。フェーズの最終ステージの goal ならゲートを評価する。ゲートの訪問は最終ステージの訪問の番号
- unknown は escalate になり、中止で答えるので中止
- end_state は、宣言したステージと状態の組ごとの戻りの回数で判定する。回数が max 以上なら中止、そうでなければ回数を 1 増やして戻す。ゲートが end_state を返した時は、最終ステージの同じ名前の辺と同じ回数を使う（ゲートを揺らす実行では review/changes_requested を review の評価とゲートが分け合う）
- unit_test の変種 defect は、markov の goal の実装（ok、ok_b）がどちらも rounds_total なので、いつも impl_defect

計算は二通りで行った。

- **厳密な計算:** 状態（いまのステージ、ステージごとの訪問の区分、辺ごとの戻りの回数）を後ろから再帰でたどった（`synthesize` は前へ流すので、別の方法になる）。状態は 308,211 個
  - markov の 70 個、ゲートを揺らす実行の 72 個の (scope, 対象, 区分, 結果) のすべてで、`synthesize` の `visit_outcomes` との差は最大 7.4e-15、`evaluations` との差は最大 8.8e-15
  - 完了の確率の差は 2.4e-15
  - implement の訪問の回数は、平均の差が 4e-15、分散 1.36821（ゲートを揺らす実行では 1.83010）は一致
- **標本:** 同じ規則の模擬を各 8,000,000 回走らせ、平均と散らばりが厳密な値と合うことを確かめた

### 1.2 本体が設計どおりか（実際のランタイム）

- 320,000 回の実行で、本体の例外、契約違反、範囲外のファイルの警告、指標の測定の失敗は一度も無かった。印が goal なのに結果が unknown になった評価も無かった
- markov の 160,000 回では、5 つのフェーズのゲートはいつも goal だった。ゲートを揺らす 160,000 回では、goal 以外のゲートの結果は assurance の changes_requested だけだった。design.py の「無いフェーズのゲートは常に goal」の仮定は成り立つ
- 160,000 回をまとめた実測は、厳密な値と合った
  - markov: 70 個の量の最大 |z| 1.9（Poisson の尺度）。完了の割合の z = −0.62、implement の訪問の回数の平均の z = −0.95
  - ゲートを揺らす実行: 72 個の量の最大 |z| 2.65。完了の z = −0.34、訪問の回数の z = 0.16

## 2. 基準ごとの表

- visit で絞った基準の E[n] は、400 × そのステージに一度でも達する確率で、`evaluations[(stage, 対象, 1)]` の 400 倍と一致する。たとえば analyze は 400 × 0.97
- from_visit で絞った基準の E[n] は、区分 2 の評価の回数の期待値の 400 倍。implement の訪問 2 以降は 0.80067 回/実行で、訪問 1 の 0.85938 と足すと mean_visits 1.66005 になる（訪問はいつも評価される）。release の訪問 2 以降は、release に達する確率 0.70753 × 0.23 = 0.16273
- 一回の実行に、条件に合う評価が複数ありうる基準（implement の訪問 2 以降）でも、分母を E[n] にとった二項の SE が正しい。各評価の結果は、それまでの経過を与えると同じ p で引かれ、条件に合うかは評価の前に決まっているから。標本でも、試行の間の観測値の標準偏差は 0.0168 で、SE 0.01676 と一致した（実際のランタイムの 400 ブロックでは 0.0166）
- mean_visits の SE: `visits_variance` は、実行ごとの訪問の回数（訪れなかった実行は 0）の、実行の間での分散。判定（訪問の番号の最大の、全実行での平均）と同じ量を見ている
  - 標本の 20,000 試行での平均の標準偏差は 0.0588、実際のランタイムの 400 ブロックでは 0.0554 で、SE 0.0585 と合う
  - 訪問の回数の分布は右に歪むが、400 回の平均では効かない。落ちる確率は標本で 0.125%、正規近似の両側 3.25 SE では 0.115%

どの基準も、分母が 30 を下回ることは事実上無い。

- 一番小さいのは release の訪問 2 以降（E[n] 65.1）

### 3.2 基準の集まりごと

| 基準の集まり | 模型（20,000 試行） | 実際のランタイム（400 ブロック） |
| --- | --- | --- |
| markov.yaml: どれかが落ちる | 1.16% | 5/400 = 1.25%（Wilson 95% [0.54%, 2.89%]） |
| markov_gated.yaml: どれかが落ちる | 0.31% | 1/400 = 0.25%（[0.04%, 1.40%]） |
| markov_shifted.yaml: どれかが通る | 0.035% | 1/400 = 0.25%（[0.04%, 1.40%]） |

- markov.yaml で落ちた 5 ブロック（基点 1056800、1094400、1095200、1138000、1154800）は、どれも一つの基準だけが外れた。偏りは無い
- ずらした基準が通った 1 ブロック（基点 1056800）は、unit_test の訪問 1 の impl_defect が 44/339 = 0.130（設計値から −4.0 SE）になった。正しい [0.14, 0.30] が落ち、ずらした [0.03, 0.13] が通った。隙間 0.01 の隣り合う幅なので、極端な標本では入れ替わる。模型では「ずらした基準のどれかが通る」確率が 0.035% で、400 ブロックで 1 回以上起きる確率は約 13%。異常ではない
- 既定の種 20000、50000 では、正しい基準はすべて通り、ずらした基準はすべて落ちる。ただし、ゲートを揺らす実行の種 50000 では、統計ではなく環境による失敗を一度見た（M2）
- F3 の toy-minimal（N=200）の「正しい基準のどれかが落ちる」は 1.2%（模型）だった。基準の数は 12 個と 5 個で違うが、同じ水準にある

### 高

なし。

### 中

**M1 release の訪問 2 以降の goal の基準は、正規近似が合わず、本当の誤判定の確率が注記の約 8 倍ある。報告の区間も、回数が足りないと示す**

  - 注記の「下側 3.3 SE」から読める落ちる確率は 0.05%
  - 二項分布の混合で厳密に出すと 0.367%
  - markov.yaml 全体の誤判定の確率 1.16% の約 3 分の 1 が、この基準一つから来ている
- adopting.md 第12節は「区間が基準の幅より広ければ、実行の回数が足りない」とする。この基準では、Wilson の 95% 区間の幅が基準の幅 0.10 より広くなる試行が 38%（実際のランタイムでは 155/400 = 39%）ある。たとえば 62/65 で区間の幅は 0.111 になる
- 基準の値（中心と E[n]）は正しい。規則（両側に約 3 SE）にも字義どおり従っている。問題は、p が 0 か 1 に近く E[n] が小さい時に、正規近似の SE で幅を決める規則の限界にある
- 直す案（どれか一つ）
  - min を 0.88 にする: 厳密な落ちる確率 0.059%（4.3 SE）で、ほかの基準と同じ水準。ずらした基準 [0.65, 0.85] とは重ならない。ほかの min での確率は、0.89 で 0.154%、0.87 で 0.022%
  - runs を 800 にする: min 0.90 のままで 0.0095%。実行の時間は倍になる
  - 注記を、厳密な確率（0.37%）が分かる書き方に直すだけにとどめる
- 手引き（adopting.md 第12節）にも、E[n]·min(p, 1−p) が小さい（目安として 10 未満）時は二項分布の裾から幅を決める、と書くとよい

**M2 例の指標が、ツールの異常終了の結果も覚えるため、一度の環境の不調が実行の集まり全体の分布を変え、正しい基準を落とす**

- 基準そのものの欠陥ではない。ただし、実際のランタイムでの誤判定の割合に効く
- 何が起きたか: 複製の上で最初に走らせた、markov_gated.yaml の既定の種 50000 の実行（400 回）が、4 つの基準のうち 3 つで落ちた
  - 完了の割合 0.265、implement の訪問の回数の平均 1.43、ゲートの訪問 2 以降の分母 23 で min_samples 未満
  - 同じ種の実行をあと 6 回走らせた。基準をかけたのは 5 回（4 回は並列）で、別の 1 回は例外の有無だけを見た。ほかに、複製の上の tests/test_stochastic.py で 1 回走らせた。どれも決まった同じ結果で、基準をかけたものはすべて通り、例外は無かった。800 ブロックの掃引でも一度も起きていない
- 同じ種の正常な実行と、一回ずつ突き合わせた
  - 400 回のうち 203 回が分かれた
  - 分かれ目は、implement の goal の変種が unknown と判定された評価（176 回。訪問 1〜5）と、intake の本体の例外（26 回。intake の評価の前に終わった実行の数と、例外の数から推した）
  - この実行の数分後に見た時点で、機械のスワップ 7 GB は使い切られていた。ほかの検証も同時に動いていた。実行の最中の状態は見ていない
- 仕組みを再現した: software_factory/metrics.py の `_run` に手を入れ、最初の compileall の子プロセスを一度だけ異常終了（終了コード −9）させた
  - 終了コードが 0 でないので、`build_passes` は False を返す。結果は `_RESULTS` に内容のハッシュで覚えられる
  - 以後、その実装の内容を持つ implement の評価は、goal が選択肢から外れる。印の goal は選択肢に無いので、結果は unknown になる
  - markov.yaml の種 20000 では、完了 0.258、implement の訪問 1 の goal 0.350 になり、12 個のうち 5 個が通らなかった（うち 1 個は分母 28 で min_samples 未満）。最初の不調な実行と同じ形
  - intake の本体の例外の原因は特定できなかった（例外の文面を記録していなかった）
- 今の検査ではこれを見分けられない
  - tests/test_stochastic.py の test_bodies_keep_the_contract は、markov の実行の集まりで本体の例外と警告だけを見る。ゲートを揺らす実行の集まりは見ない
  - 印が goal なのに指標が落ちた評価は、どちらの集まりでも見ていない
  - 再現した失敗では本体の例外も警告も出ないので、「本体の分布が設計とずれている」としか見えない
- 直す案
  - 指標: ツールの子プロセスが異常終了した時（終了コードが負、シグナル、時間切れ）は、結果を覚えずに `MetricError` を上げる。終了コード 0 と 1 のように、意味の決まった結果だけを覚える
  - 検査: 分布テストに使う実行の集まり（markov と gated の両方）で、次がどれも無いことを確かめる
    - 本体の例外
    - 指標の測定の失敗
    - 印が goal の評価で goal が選択肢に無かったもの（tests/stochastic.yaml の metrics_fail が空の変種で、指標が落ちたもの）

### 低

**L1 ずらした基準 analyze needs_unclear [0.0, 0.17] が、正しい [0.17, 0.33] と端 0.17 を共有する**

- 観測値がちょうど 0.17 なら、正しい基準もずらした基準も通る。確率は 1.6e-10 で実害は無い
- 「すぐ外側」の意図に合わせ、max を 0.16 にするとよい（設計値から 4.1 SE）

**L2 release の訪問 1 の notes_incomplete [0.15, 0.31] は 3.198 SE で、注記の規則「3.2 倍以上をとり、0.01 の単位で外側に丸めた」をわずかに下回る**

- p ± 3.2 SE は [0.14995, 0.31005] で、外側に丸めると [0.14, 0.32] になる
- 落ちる確率は、今の幅で 0.141%、[0.14, 0.32] で 0.034%
- ほかに、注記の倍数に丸めの差がある。acceptance の「3.6」は、正確な SE では 3.54。status_rate の「両側 3.4」は、上側が 3.52
- 幅を規則どおりに直すか、規則の書き方を「およそ 3.2 倍」に改める

**L3 markov_gated.yaml には、ずらした基準が無い。四つのうち二つ（status_rate と mean_visits）は、ゲートを揺らさない本体も通す**

- ゲートを揺らさない本体（完了 0.6885、訪問の回数 1.660）をこの二つにかけると、status_rate は 99%、mean_visits は 57% の確率で通る
- ゲートの分布が効いているかを確かめているのは、ゲートの二つの基準だけ。ゲートの束縛が抜ければ割合が 0 になるので、それは落とせる
- markov_gated の「ずらした基準」を足すとよい。例:
  - ゲートの訪問 1 の changes_requested [0.35, 0.50]（上へ約 5.7 SE）と [0.0, 0.10]（下へ約 3.8 SE）
  - status [0.75, 0.90]（上へ 3.8 SE）
- 注記には、二つの基準が揺らす前後を見分けないことを書くとよい

**L4 test_correct_expectations_follow_the_design は、幅の下限（3 SE 以上）だけを確かめ、上限を確かめない**

- 正しい基準の幅を広げても（たとえば [0.0, 1.0]）、このテストは通る。ずらした基準は固定の値なので、正しい幅とずらした幅が重なっても気づかない
- 幅が 5 SE 以下であること、または正しい幅とずらした幅が重ならないことも確かめるとよい

**L5 `visits_variance` の説明「一回の実行の中での訪問の回数の分散」は、訪れなかった実行を 0 として含むことが読み取りにくい**

- 中身は正しい。実行ごとの訪問の回数を、訪れなかった実行も 0 として含めた分散で、mean_visits の判定（全実行の平均）と同じ量を見ている
- ただ、「一回の実行の中での」は、実行の中のばらつきとも読める。達した実行だけで分散をとると、SE を誤る
- adopting.md 第12節と api-reference.md の `Prediction` に「実行ごとの訪問の回数（訪れなかった実行は 0）の、実行の間での分散」と書くとよい

## 5. 実験の再現

スクリプトは、検証役の scratchpad にある（リポジトリには置いていない）。

- 自前の模型（後ろから再帰でたどる厳密な計算と、標本の模擬）
- 実際のランタイムの掃引（`run_set` を直接呼び、ブロックごとに `evaluate_expectations` をかけ、実行ごとの評価、状態、例外、指標の失敗を記録する）
- 二項分布の混合による厳密な確率
- 指標の異常終了の注入

同じことは、次の手順で再現できる。

1. 互いに重ならない 400 回ずつの種のブロックで `run_set("markov", 400, 基点, workdir, gates=...)` を回す
2. 三つの expectations をかける
3. `design_model` に `synthesize` をかけた値と比べる

## 利用者への指摘（公開の文書の語だけで）

基準（tests/expectations/ の三つ）は、設計値から正しく導かれている。中心、E[n]、標準誤差は、`synthesize` の `evaluations`、`visit_outcomes`、`visits_variance` と独立な計算の両方と一致した。基準はそのまま使える。次の二点は改善として勧める。

### 1. release の訪問 2 以降の goal の基準 [0.90, 1.0] は、正規近似の幅が合わない

- p = 0.97、条件に合う評価の数の期待値 E[n] = 65.1 なので、外れる側の期待件数は約 2 件しかない。二項分布が歪む
  - 注記の「下側 3.3 SE」なら、落ちる確率は約 0.05% のはず
  - 二項分布で厳密に計算すると約 0.37%
  - markov.yaml 全体で正しい基準のどれかが落ちる確率（約 1.2%）の、3 分の 1 がこの基準から来ている
- `ExpectationReport.lines()` の Wilson の 95% 区間の幅も、約 4 割の実行で基準の幅 0.10 を超える。adopting.md 第12節の読み方では「回数が足りない」にあたる
- 次のどれかにするとよい
  - min を 0.88 にする（落ちる確率 0.06%、ほかの基準と同じ水準。markov_shifted.yaml の [0.65, 0.85] とは重ならない）
  - runs を 800 にする
- 一般に、E[n]·min(p, 1−p) が小さい（目安として 10 未満）基準は、標準誤差の倍数ではなく、二項分布の裾の確率から幅を決める

### 2. 例の指標が、ツールの異常終了の結果を覚えてしまい、一度の環境の不調で正しい基準が落ちる

- software_factory/metrics.py は、ツールの結果を指標名、引数、内容のハッシュで覚える。adopting.md 第4節が許す使い方だが、子プロセスが異常終了した時の値も覚える
  - たとえば `build_passes` と `tests_pass` は、終了コードが 0 でなければ False を返して覚える
  - メモリの逼迫などで一度でも異常終了すると、同じ内容の評価はその後ずっと goal が選択肢から外れ、印の goal が unknown になる
- 実際に、markov_gated.yaml の既定の種で、ほかの検証と同時に走らせた一回の実行が、四つの基準のうち三つで落ちた（完了 0.265）。同じ種の実行は、基準をかけたほかの 6 回（tests/test_stochastic.py を含む）すべて通った
- 子プロセスを一度だけ異常終了させると、同じ形の失敗（markov.yaml で完了 0.258、12 個のうち 5 個が通らない）を再現できた
- 次の二つを直すとよい
  - 指標: 終了コードが負、シグナル、時間切れの時は、結果を覚えずに `MetricError` を上げる。意味の決まった終了コード（0 と 1 など）の結果だけを覚える
  - 検査: 分布テストに使う実行の集まり（ゲートを揺らす集まりも含めて）で、次が一つも無いことを確かめる
    - 本体の例外
    - 指標の測定の失敗
    - tests/stochastic.yaml の metrics_fail が空の変種（印が goal）なのに goal が選択肢から外れた評価
  - 今の test_bodies_keep_the_contract は、ゲートを揺らさない集まりの例外と警告しか見ないので、この失敗を見分けられない
