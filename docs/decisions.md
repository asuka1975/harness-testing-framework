## #1 成果物宣言の形

- 状態: 承認（2026-10-21、包括指示による推奨の採用）
- 強制点: F1（拡張スキーマを書く時）。先送りすると拡張スキーマに着手できないので、F1 で決めざるを得ない
- 関係: #2（指標の入力）、#5（フェーズの集約述語の入力）
- 決定: (c) reads / writes と memory\_in / memory\_out

### 文脈

ステージが何を読み、何を書き、何を記憶として次へ受け渡すかの宣言。チェックポイントが保存・復元する範囲、carry の生成と消費の検査、分類器に渡す状態文書への投影の三つの入力になる。

### 選択肢と帰結

- (a) 宣言なし
  - スキーマとワークフロー定義が最小で、作者の負担が無い
  - carry の生成と消費を静的に検査できない。第6節 F1 の完了条件にある検査器の性質「carry の生成と消費」が書けない
  - チェックポイントの範囲が決まらない。作業領域全体を保存するか、範囲をハーネスごとに決めることになる
  - 分類器に渡す状態文書への投影（第3節 #1 の推奨の理由、第6節 F2 の oracle 基盤の「投影」）を宣言から導出できない。状態をそのまま渡すか、投影をハーネスごとに書くことになる
- (b) reads / writes のみ
  - ファイル単位の検査（読む成果物が前段で書かれているか）と、チェックポイントの範囲（writes の和）は導出できる
  - ファイルでない受け渡し（carry）の出どころと行き先を宣言できないので、carry の検査ができない
- (c) reads / writes に加えて memory\_in / memory\_out
  - carry の検査（carry の各項目が元ステージの memory\_out と戻り先の memory\_in の両方にある）、チェックポイントの範囲（writes と memory の和）、投影（そのステージの reads / writes / memory を状態文書に写す）が、すべて宣言から導出できる
  - 作者は各ステージに四つの一覧を書く
  - 宣言と実際の振る舞いのずれ（宣言外の書き込み、宣言した writes の欠落）は静的には捕まらないので、ランタイムが実行時に検査する必要がある
  - 付録 B の例がこの形

### 推奨

(c)。carry の生成と消費の検査、チェックポイントの範囲、分類器に渡す状態文書への投影が、すべてこの宣言から導出される（第3節の推奨の理由）。

### 計画書との整合

(a) と (b) は、第2節の固定判断「ロールバック」（carry の各項目を memory\_out と memory\_in に宣言する）、付録 B、第6節 F1 の完了条件（carry の生成と消費）と合わない。第2節は「再検討しない」とされているので、(a) か (b) を選ぶことは固定判断の変更になる。

### (c) を採った場合に F1 のスキーマ案で示す下位の設計点

ここでは決めない。拡張スキーマの案と一緒に提案し、F1 のスキーマ承認で確定する。

- reads / writes にパスのパターン（glob）を許すか
- ワークフローの外から与えられる入力（最初のステージが読むもの）をどこに宣言するか
- memory の項目に型を持たせるか（名前だけか、値の形も宣言するか）

## #2 指標レジストリ

- 状態: 承認（2026-10-21、包括指示による推奨の採用）
- 強制点: F1（拡張スキーマの quantitative の形を決める時）。先送りすると拡張スキーマと検査器の「指標の存在」が書けない
- 関係: #1、#5（フェーズの集約述語も指標になる）
- 決定: (b) YAML には指標名と基準だけ、実装はハーネス側のレジストリ。検査器は参照する指標がすべてレジストリにあることを検査する

### 文脈

goal の quantitative に書く各指標（ファイルの有無、テストの結果、カバレッジ、承認など）を、どこでどう定義し実装するか。

### 選択肢と帰結

- (a) 指標の判定式を YAML に書き、フレームワークのコードが解釈する
  - ワークフロー定義だけで指標の意味が完結し、ハーネス側のコードが要らない指標がある
  - フレームワークに式言語とその解釈器が要る。ビルドやテストの実行のように外部ツールを伴う指標は式で書けないので、式言語にコマンド実行を入れるか、結局ハーネス側の実装を呼ぶ口が要る。前者は本体に外部コマンドの実行とその出力の解釈を持たせることになり、本体がツールの出力形式に依存しやすくなる（第5.8節の趣旨に反しやすい）
  - 「その指標を決定論的に実装できるか」の判断がワークフロー定義のレビューに入り込み、人間が見るべき記述のレビューとコードのレビューが混ざる
- (b) YAML には指標名と基準（description と equals / min / max）だけを書き、実装はハーネス側のレジストリに置く
  - 契約に指標のインターフェース（スナップショットを受けて値を返す）と、レジストリ（実行せずに名前の一覧を列挙できる）を加える
  - 基準との比較（equals / min / max）はフレームワークが行い、ハーネスは測定だけを行う。比較の意味が全ハーネスで揃う
  - 整合性検査器は「YAML が参照する指標がすべてレジストリにある」を検査する。このため検査器はハーネスのレジストリを入力として受け取る（受け取り方は契約で決める）
  - 人手の承認（human\_approval）のような指標も、ユーザー入出力を使うレジストリの一実装として扱える

### 推奨

(b)。「YAML が参照する指標がすべてレジストリにある」を整合性検査に含める。

### 計画書との整合

(a) を選ぶと、付録 B の検査項目「quantitative の指標名が指標レジストリにあること」、第4節の metrics/（指標レジストリの実装）、第6節 F2 の oracle 基盤の「指標レジストリの仕組み」、F4 の目的（実在の決定論指標が指標レジストリに乗ること）の改訂が要る。

### (b) を採った場合に F1 で提案する下位の設計点

- 指標が引数を取れるか（例: 変更してよいパスの範囲）。取れない場合は、引数の組ごとにレジストリの項目を分ける
- 指標の値の型（真偽値と数値に限るか）
- 測定そのものが失敗した時（ツールが起動しない等）の扱い。goal 未達として end\_state の分類へ進めるか、直ちに unknown にするか

## #3 escalate 後の人間の選択肢

- 状態: 承認（2026-10-21、人間の回答「全て推奨で」）
- 強制点: F2（runner）。計画書の契約の定義（第2節、第6節 F1）には人間の応答の受け口が無いので、F1 で要るのは下記の追加の提案（運用者向けのインターフェース）を採る場合に限る
- 関係: #4（応答の受け口）、追加の論点 A（戻り先の制約）
- 決定: 四つすべて（再実行 / 指定ステージへロールバック / goal 到達扱いで続行（注記つき）/ 中止）。運用者向けの応答インターフェースの追加の提案も採る

### 文脈

rollback が max を超えた時と、評価が unknown になった時に escalate し、人間が次の操作を選ぶ。runner がどの選択肢を受け付けるか。

### 選択肢と帰結（各選択肢を採るか採らないか）

- 再実行: escalate したステージを、その開始時スナップショットから実行し直す
  - 一過性の失敗（LLM の揺らぎなど）に対処できる
  - 選択後に、超過した辺の回数を数え直すかの規則が要る
- 指定ステージへロールバック: 人間が戻り先を選ぶ
  - ワークフロー定義に無い遷移なので、検査器は静的に検査できず、ランタイムが実行時に検査する（戻り先がそのステージより前か、など）
  - carry を人間が指定できるか、指定できるなら memory\_in の宣言に従わせるか、の規則が要る
- goal 到達扱いで続行（注記つき）: goal を満たしていない成果物のまま次へ進む
  - 人間の判断で止まった実行を救える
  - 注記をスナップショットと実行記録に残し、後段のゲートとレポート（分布テスト、カバレッジ、遷移行列の推定）で区別できるようにする必要がある。区別しないと、強制通過が分布の推定を汚す
- 中止: 実行を終了状態「中止」で終える。最後のスナップショットは残す
- 一部だけ採る場合: runner の状態とテストは減るが、第6節 F2 の完了条件「escalate の4つの選択肢が動く」の改訂が要る

### 推奨

四つすべて。runner はこの四つを受け付ける。

### 採った場合の下位の設計点

- 追加の提案（採るなら F1 の契約、progress.md の T4 に入る）: 人間の応答の受け口を、ステージ本体が使うユーザー入出力（#4）とは別の、運用者向けのインターフェースとして契約に加える。テストではどちらにもシミュレータを束縛する
- F2 で提案: 選択後に、超過した辺の回数を数え直すか

### 人間の質問への回答（2026-10-21）

質問: 「gate を通らなかったときで rollback 条件を満たさなかったときは、そのステージの最初に戻る認識で合っているか」

回答: 自動では戻らない。第2節の評価順序（goal 指標 → goal 定性判定 → end\_state 分類 → unknown）では、goal を満たさず、どの end\_state にも当たらない結果は unknown（例外系）になり、escalate して人間に差し戻す。分類器の確信度が閾値未満の時も unknown になる。人間が escalate 後の四つの選択肢から「再実行」を選んだ時に、そのステージの開始時スナップショットから実行し直す。自分自身へのロールバックを禁止した追加の論点 A とも整合する。自動でステージの最初に戻す規則は第2節の固定判断（unknown は人間に差し戻す）の変更になるので、望む場合は改めて指示してほしい。

追記（2026-10-22）: 人間の指摘「そのステージをもう一回やり直したいパターンがカバーできていない」を受けて、自分自身へのロールバックを許した（A2）。やり直したい状態を end\_state として書き、戻り先にそのステージ自身を指定すれば、carry を持って自動でやり直せる。どの end\_state にも当たらない結果は、従来どおり unknown として人間に差し戻す。

## #4 ユーザー回答待ちの表現

- 状態: 承認（2026-10-21、人間の回答「全て推奨で」）
- 強制点: F2（runner。計画書の指定）。ただしユーザー入出力のインターフェースは契約の一部（第2節、第6節 F1）なので、F1 で契約を書く時点で実質的に必要になる
- 関係: #3、追加の論点 A
- 決定: (b) runner が中断状態を持ち、ステージ本体はユーザー入出力インターフェースで同期的に待つ

### 文脈

ステージの途中でユーザーの回答が要る場合（要求の取り込みなど）を、ワークフローの上でどう表すか。

### 選択肢と帰結

- (a) end\_state の一つとして持つ（例: 回答待ち）
  - runner に中断の状態が要らない
  - 回答の後に戻る先は自分自身になり、付録 A の rollback.stage の説明「このステージより以前」と、付録 B の検査項目「戻り先がそのステージより前にあること」に当たらない（追加の論点 A）
  - 回答を carry で運ぶことになるが、回答はステージの記憶ではなく外部からの入力なので、memory\_out に宣言する意味が崩れる
  - 分類器が「回答待ち」を分類することになり、待ちが end\_state の分布に混ざって、分布テストと独立性検証を汚す
  - ユーザー待ちのたびに辺の max を消費する
- (b) runner が中断状態を持ち、ステージ本体はユーザー入出力インターフェースで同期的に待つ
  - 分類体系がステージの振る舞いだけを表す
  - 契約にユーザー入出力のインターフェースが加わり、テストではそこにユーザーシミュレータを束縛する
  - runner に「中断」と「再開」の遷移が要る。回答に長い時間がかかりプロセスを跨いで再開するなら、中断時に保留中の質問をスナップショットに残し、再開時はそれまでの回答を recorder の記録から再生してステージを再実行する、といった設計が要る（F2 で提案）

### 推奨

(b)。テストではユーザー入出力にシミュレータを束縛する。

### 計画書との整合

(a) を選ぶと、第6節 F1（toy-minimal の「ユーザー待ち」）、F2（runner の中断）、F4 の完了条件（ユーザー待ちのステージ）の意味が変わる。

## D-8 F3 のランナーの判定の規則（2026-10-22）

- 状態: 承認（2026-10-22、包括指示による推奨の採用。閾値と基準は仮置きで、F3 の検証役の判定と、人間の確認を経る）
- 強制点: F3
- 関係: plan.md 第2節（分布基準の置き場、組み合わせテストはしない、分類器の検証）、第6節 F3、D-7
- 決定: 下記のとおり

### 文脈

分布テスト、独立性検証、E2E、マルコフ合成、分類器の検証には、判定の規則と既定値が要る。計画書は閾値をすべて仮置きとし、人間が確定するとしている。

### 選択肢と帰結

各点の推奨と理由だけを書く。

- **分布テスト:** 観測値が [min, max] に入れば通る（計画書の「80% 以上」という書き方に合わせた点推定の判定）
  - 報告に Wilson の 95% 区間とその幅を添え、実行の回数が基準の幅に対して足りるかを人が見られるようにする
  - 条件に合う評価が無い基準は「判定できない」で通らない
  - 既定の回数は小さく（玩具は 200）、環境変数 HTF_RUNS で変える
- **玩具の基準の決め方:** 確率的な偽の本体の設計値（tests/stochastic.yaml）から手で導く
  - 基準の幅は、設計値の両側に既定の回数での標準誤差のおよそ 3 倍
  - 設計値から外したずらした基準（markov\_shifted.yaml）は、すべて落ちることを確かめる
- **独立性検証:** カイ二乗統計量の並べ替え検定にする。小さい期待度数でも近似に頼らず、追加の数値計算の実装が要らないため
  - 既定値は alpha 0.01、並べ替え 2000 回（種 0）、代表ごとに 10 件以上
  - 代表は、ステージが書いた成果物の内容のハッシュ
  - 十分な件数の代表が二つ未満なら「判定できない」
- **マルコフ合成:** クラスの分布は (ステージ, 訪問の区分) で決まると仮定する。訪問の番号は cap 以上を一つにまとめ、既定は 2（初回とそれ以降）。ゲートは (フェーズ, 最終ステージの訪問の区分)
  - escalate の後の方針は中止だけを扱い、方針は明示の引数にする
  - 予測と実測の一致は、差が標準誤差の 4 倍以内とする
  - 玩具の markov の本体は、仮定が成り立つように作ってある。一致は合成の計算の確認で、マルコフ性という方法の検証ではない（plan.md 第1節）
- **E2E のカバレッジ:** 全ステージ goal の実行一つと、goal 以外の (ステージ, クラス) ごとに一つの実行
  - 対象のステージの最初の訪問だけを対象のクラスにする
  - 誘発の台本があれば誘発、無ければ注入（分類の結果だけを変える）
- **分類器の検証:**
  - ECE は確信度を [0, 1] の等幅 10 区間に分け、最後の区間は 1 を含む
  - 答え無しは独立のカテゴリとして数え、確信度 0 の不正解として較正に入れる
  - 再実行の一致率は、同じ項目を既定 2 回分類して、すべて同じ答えの割合
  - 偽の分類器の配分は決定論的にし、κ と ECE の期待値を厳密に計算できるようにする
- **トリアージ:** 待ち行列に入れる条件は、結果が unknown か、確信度が引数の閾値未満
  - 判定は五種類で、分類体系の変更は提案として記録するだけ
- **expectations は保護ファイル（D-7）:** 玩具の expectations は計画エージェントが書き、F3 の検証役が基準を確かめる

## D-9 F3 の検証で見つかった点の扱い（2026-10-22）

- 決定: 下記のとおり

### 文脈

検証役の F3 完了判定は準正常（高 1、中 6、低 13）。分布基準とオラクル検証の期待値は、検証役が独立に導き直して一致した。一方で、独立性検証がフェーズの最終ステージの goal を検査できない、答え無しの扱いが ECE を下げる、などの欠陥が指摘された。

### 選択肢と帰結

各点の推奨と理由だけを書く。

- **独立性検証の「次の状態」（D-8 の置き換え）:** 続くゲートの評価をつなぎ、その次のステージの評価までを次の状態にする。理由: フェーズの最終ステージの goal の後は必ずゲートで、ゲートだけを次の状態にすると下流の違いが見えない
- **独立性検証の層:** 状態と訪問の区分（マルコフ合成と同じ cap、既定 2）の組ごとに検定する。理由: マルコフの仮定の下で、訪問による成果物と下流の違いをクラスの粗さと取り違えない
- **独立性検証の判定の名前:** `independent` を `not_detected` に改める（「検出しなかった」の意味）。状態ごとに独立に検定し、多重性の補正はしない（違反の疑いは人がトリアージで確かめる）
- **代表の鍵:** `record_run` の引数で変えられる。LLM の出力では、意味の近い成果物を同じ鍵にまとめる関数を与える
- **分布テストの回数（D-7・D-8 の置き換え）:** HTF_RUNS は回数を増やすだけで、減らせない。0 以下の値は誤り。各基準に `min_samples`（既定 30）を置き、分母がそれ未満なら判定できず通らない。理由: 幅は既定の回数から決めてあり、回数を減らすと誤判定が増える
- **玩具の expectations:** 幅を E[n] での標準誤差のおよそ 3 倍に揃え、根拠を注記した。ずらした基準に、下へのずれと、正しい幅のすぐ外側の幅を足した
- **分類器の検証の ECE（D-8 の置き換え）:** 答えた項目だけで計算し、答えた割合を別に出す。理由: 答え無しを確信度 0 の不正解として入れると、答え無しが多いほど ECE が下がる
  - 分類器の出力は、ランタイムと同じ規則で「答え無し」に正規化する（共通の関数 `safe_classify`）
  - 対象ごとの内訳を出す
- **項目の id:** コーパスとトリアージの項目の id は、実行の一意な id（実行記録の内容のハッシュの先頭 16 桁）と評価の seq。理由: 同じ種で設定を変えた実行の項目が黙って捨てられない
- **トリアージ:** `classifier_error` の判定にも正しいクラスを書けるが、選択肢のどれかに限る
- **テストの追加:**
  - `compare_prediction` と `mean_visits` が落ちることを確かめるテスト
  - Wilson の区間の公表値のテスト
  - 並べ替え検定と超幾何分布の厳密な p 値との比較
  - 訪問の区分が 3 以上の合成
  - 玩具で、設計値から作った厳密なモデルの予測と実測の比較
- **残す制限（F5 までに検討）:** 誘発の確認はいつも台本の分類器で行い、実の分類器が誘発した成果物をそのクラスに分類するかは見ない（低-9）
- **再検証（二回目）の後の追加（2026-10-22）:**
  - 独立性検証の層に、次のステージの評価の訪問の区分も加えた（代表が「どこから戻ってきたか」で変わる場合の誤検出を防ぐ）
  - 答えた項目が無い時の ECE は「無し」（0 と出すと完全な較正に見える）
  - adopting.md 第12節の、片側の基準の下限を要件より下げて置く手引きを取り消し、「要件の値をそのまま min に置き、緩めない。足りなければ回数を増やす。基準の値は人間が決める」に改めた（plan.md 第5.5・5.6節）
  - ずらした基準の ask\_topic を、正しい幅と端を共有しない [0.11, 0.25] にした
  - cap の扱い、対象ごとの内訳、コーパスの項目 id のテストを足した
  - 第5.3節の上限（仕様以外への差し戻しは 2 回まで）に達したので、三回目の判定は依頼せず、v0.1 の公開の承認の時に残りを人間に示す
