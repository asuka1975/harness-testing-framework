# ハーネス契約 v0.1

状態: 承認（2026-10-22、plan.md 第6節 F1 の人間ゲート。自分自身へのロールバックを許す修正を含む）。

この文書は、フレームワークとハーネスの境界を定める。フレームワークは契約と参照ランタイムを提供する（決定 #8）。ハーネスは、契約を満たすもの（ワークフロー定義、ステージ本体、指標の実装、ユーザー入出力、LLM クライアント）を提供する。契約は特定の言語に依存しない。Python の束縛は `harness_testing_framework.contract` にある。

## 1. 用語

- **ワークフロー定義**: schema/workflow.schema.json に適合する YAML。遷移とゲートの唯一の情報源
- **作業領域**: ステージ本体が読み書きするディレクトリ。成果物（artifacts の reads / writes）はここからの相対パスで指す
- **範囲**: ワークフローの inputs と、全ステージの writes の和。スナップショットはこの範囲のファイルだけを持つ。末尾が / のものはディレクトリの下全体
- **記憶**: 名前つきの値（JSON で表せる値）。memory\_in / memory\_out で宣言し、carry で戻り先へ運ぶ
- **スナップショット**: ある時点の、範囲内のファイル、記憶、ゲートの状態、注記の組（第5節）
- **辺**: rollback の一項目。元ステージ、end\_state、戻り先の組で識別する。戻り先は元ステージ自身か、それより前のステージ（決定 A2）
- **訪問**: 一回の実行の中で、あるステージに入った回数（1 から数える）
- **実行**: ワークフローの最初のステージから、完了・中止・中断までの一続き。実行ごとに種（seed）を持つ

## 2. 三つの操作

### 2.1 run(stage, snapshot) → snapshot

ステージの開始時スナップショットからステージ本体を一回実行し、終了時スナップショットを返す。

1. ランタイムは、スナップショットの範囲内のファイルだけを持つ新しい作業領域を用意する
2. ステージ本体を一回呼ぶ（第7.1節）。本体は作業領域のファイルを読み書きし、memory\_out に宣言した記憶を書く
3. ランタイムは作業領域を走査して終了時スナップショットを作る。範囲内のパスのうち、このステージの writes に無いものが変わっていたら契約違反（第8節）。変化には、内容の変更、新しいファイル、削除のすべてを含む。範囲外のファイルは捨てる（実行記録に警告として残す）
4. 本体が memory\_out に無い記憶を書いたら契約違反
5. 宣言した writes を本体が書かなかったことは、契約違反にしない。ステージがうまくいかなかった結果としてありうるので、指標と分類で扱う

本体が例外で終わった場合と契約違反の場合は、評価をせずに、理由つきで unknown として扱い escalate する（第4節）。

### 2.2 evaluate(stage, snapshot) → class

終了時スナップショットを評価し、`goal`、unknown 以外の end\_state の id、`unknown` のいずれか一つを返す。`goal` と `unknown` は予約語で、`goal` は end\_state の id に使えない（スキーマで禁止）。順序は固定する（plan.md 第2節）。

1. **goal 指標**: quantitative の各指標を指標レジストリで測り（第7.2節）、基準（equals / min / max）と比べる。比較はフレームワークが行う。測定が失敗した指標（指標の実装の例外と、真偽値でも数でもない値を含む）は未達とする
2. **goal 定性判定と end\_state 分類**: 分類器（第7.5節）に、状態文書（2.4）と選択肢を渡して一つを選ばせる。選択肢はワークフロー定義の記述そのもので、質問への分解や導出規則は加えない
   - 全指標が基準を満たした場合: 選択肢は goal の qualitative、各 end\_state（unknown を含む）の順
   - 一つでも満たさない場合: goal を選択肢から除き、各 end\_state（unknown を含む）だけ
3. **unknown**: 分類器が unknown を選んだ場合、確信度が閾値未満の場合、分類器が答えを返さない場合は unknown。分類器が例外で終わった場合と、確信度が 0〜1 の有限の数でない場合は「答えを返さない」とみなし、実行記録には選択無し・確信度 0 と書く

end\_state の優先順は記述の中に書かれ（決定 #7）、分類器はそれを記述として読む。フレームワークは優先順を解釈しない。

閾値はハーネスの設定で、分類器の較正結果から決める（plan.md 第2節）。決定論的なテストでは、確信度を固定した偽の分類器を使う。

### 2.3 restore(snapshot) + overlay(carry)

rollback で戻る時、ランタイムは次を行う。

1. 戻り先ステージの、直近の訪問の開始時スナップショットを取り出す（restore）。戻り先が元ステージ自身なら、いま終わった訪問の開始時スナップショット
2. 現在のスナップショットの記憶から、辺の carry に挙がった項目だけを取り出し、1 の記憶に上書きする（overlay）。現在のスナップショットに無い項目は重ねない（実行記録に残す）
3. 得られたスナップショットを戻り先ステージの新しい開始時スナップショットとし、run から続ける

carry 以外の、戻った区間で作られたファイルと記憶はすべて捨てる。ゲートの状態もスナップショットに含まれるので、戻り先の時点の状態に戻る（2.5）。

### 2.4 状態文書（分類器への投影）

分類器に渡す状態は、成果物の宣言から導出する（決定 #1）。先頭に評価の対象を示す見出し行を置き、続けて、そのステージの reads と writes に当たるファイルの内容と、memory\_out の記憶の値を、決まった順序で並べた文書にする。見出し行は、ステージなら `# 評価: stage <ステージ id> visit <訪問の回数>`、フェーズゲートなら `# 評価: phase <フェーズ id> visit <最終ステージの訪問の回数>`。ゲートの選択肢は最終ステージの選択肢と同じ形になるので、分類器が評価の対象を区別できるようにする。memory\_in（持ち帰ってきた記憶）は入れない。終了時の状態はステージが残したもので観測し、入力の記憶に分類が引きずられないようにするため。フェーズゲートの状態文書は、フェーズ内の全ステージの reads と writes の和に当たるファイルと、最終ステージの memory\_out から作る。文字として読めないファイルは、パスと大きさと内容のハッシュだけを書く。長さの上限はハーネスの設定で、超えた部分は切り詰めたことを明記する。スナップショットをそのまま分類器に渡さない。ランタイムは状態文書を内容アドレスの置き場に残し、実行記録の evaluation に SHA-256 を書く（分類器の検証のコーパスとトリアージが、分類器の見たものを読めるようにする）。

## 3. 評価の結果と遷移

| 評価の結果 | 遷移 |
| --- | --- |
| goal（フェーズの最終ステージ以外） | next: 次のステージへ。終了時スナップショットが次のステージの開始時スナップショットになる |
| goal（フェーズの最終ステージ） | フェーズゲートを評価する（3.2） |
| end\_state | rollback: その end\_state の辺の回数が max 未満なら、回数を一つ増やして戻る（2.3）。max に達していたら escalate（理由 max\_exceeded） |
| unknown | escalate（理由 unknown） |

### 3.1 回数

辺の回数は実行ごとに数え、スナップショットには含めない（restore で戻らない）。max: 2 の辺は二回まで通れ、三回目に escalate する。escalate 後の人間の選択で回数は数え直さない。人間は以後の超過のたびに判断する。

### 3.2 フェーズゲート（決定 #5）

フェーズの最終ステージが goal に達したら、フェーズの goal を 2.2 と同じ順序で評価する。

- 指標はフェーズの quantitative を測る。測る対象は最終ステージの終了時スナップショット全体で（7.2 の view）、集約述語は通常フェーズ内の各ステージの writes をまとめて見る
- 分類の選択肢は、フェーズの goal の qualitative と、最終ステージの end\_state（unknown を含む）
- goal ならゲートを通過済みにし（スナップショットに記録する）、次のフェーズの最初のステージへ進む。最後のフェーズなら実行を完了する
- end\_state なら、最終ステージのその end\_state の辺で rollback する（回数も同じ辺で数える）
- unknown なら escalate

フェーズ境界を越えるロールバックは、戻り先の開始時スナップショットを復元するので、その後のフェーズのゲートは通過済みでなくなる。再びそのフェーズの最終ステージに達した時に、ゲートを評価し直す。

この意味論からの帰結（ワークフロー定義の書き手が知っておくこと）:

- ゲートの評価は最終ステージが goal に達した直後に行うので、最終ステージの end\_state の記述がそのステージ自身の不足だけを述べていると、ゲートの不合格はどの end\_state にも当たらず unknown（escalate）になる。ゲートの不合格を自動で戻したいなら、最終ステージの end\_state の記述に、フェーズ全体の不足として観測できる条件を含める
- 最終ステージ自身をやり直したいなら、最終ステージに自分自身を戻り先とする end\_state を書く。書かなければ unknown から人間の「再実行」になる
- ゲートから rollback する時の carry は、goal に達した実行の memory\_out から取る。ゲートで使われうる end\_state の carry の項目は、goal に達した時にも書いておく

### 3.3 中断と再開（決定 #4）

awaits\_user を宣言したステージの本体は、ユーザー入出力（第7.3節）で同期的に回答を待つ。ユーザー入出力の実装は、その場で回答を返すか、回答がまだ無いことを知らせる（中断の合図）。中断の合図を受けたら、ランタイムは実行を中断状態にし、保留中の質問（文と選択肢）と、そのステージの開始時スナップショットと、その訪問でのそれまでの回答と LLM の応答を保存する。再開では、そのステージを開始時スナップショットから実行し直し、保存した回答と LLM の応答を順に再生し（外へ二度出さない）、新しい回答を続ける。

本体が中断の合図を握りつぶしても、ランタイムは中断として扱う。awaits\_user を宣言しないステージの本体が中断の合図を送ったら、契約違反とする。

再開は同じ訪問の続きで、訪問の回数を増やさない（種と記録の鍵が変わらず、それまでの回答の再生が揃う）。運用者の「再実行」は新しい訪問で、訪問の回数を一つ増やす。

### 3.4 escalate と人間の選択（決定 #3）

escalate したら、ランタイムは運用者インターフェース（第7.6節）に、理由と状況を渡して選択を受け取る。選択は四つ。

| 選択 | 動作 |
| --- | --- |
| 再実行 | escalate したステージを、その直近の開始時スナップショットから実行し直す |
| 指定ステージへロールバック | 人間が選んだステージ（escalate したステージ自身か、それより前）へ 2.3 と同じ手順で戻る。carry は人間が指定でき、戻り先の memory\_in にあるものに限る |
| goal 到達扱いで続行 | 評価の結果を goal とみなして遷移する。注記（誰が、なぜ）をスナップショットに残し、以後のスナップショットに引き継ぐ。実行記録とレポートは、強制通過を含む実行を区別できる |
| 中止 | 実行を中止状態で終える。最後のスナップショットは残す |

運用者インターフェースも、その場で選択を返すか、まだ選択が無いことを知らせられる。後者ならランタイムは実行を escalate 待ちの状態で保存し、選択を受けて再開する。条件を満たさない選択（後ろのステージへのロールバック、戻り先の memory\_in に無い carry）は拒み、警告を書いて escalate 待ちに戻す。注記の「誰が」が空なら、ランタイムは `operator` と書く。

goal 到達扱いで続行の後は、escalate したのがステージの評価なら、そのステージが goal に達した場合と同じに進む（フェーズの最終ステージならゲートを評価する）。フェーズゲートの評価なら、ゲートを通過済みにする。本体の例外か契約違反で escalate した場合は終了時スナップショットが無いので、そのステージの開始時スナップショットのまま進む。

### 3.4.1 実行記録の出来事の並び

ランタイムは次の並びで実行記録を書く（seq は実行の最初から通し番号で、中断や escalate 待ちを跨いで続く）。

- ステージの一回: `stage_start` → `stage_end` → `evaluation`（scope=stage）→ 遷移
- 遷移: `transition`（next / rollback / gate\_pass / complete / abort）。フェーズの最終ステージが goal なら、`evaluation`（scope=phase）を挟んでから gate\_pass と next（または complete）、あるいは rollback
- escalate: `transition`（kind=escalate）→ `escalation`（選択つき）→ 選択に応じた続き。続きは、再実行なら同じステージの `stage_start`（訪問 +1）。ロールバックなら `transition`（kind=rollback、edge=null）。goal 到達扱いなら上の goal の場合と同じ。中止なら `transition`（kind=abort）と `run_end`（aborted）
- 運用者が選択を保留した場合: `escalation`（decision=null）→ `run_end`（awaiting\_operator）。再開すると `escalation`（選択つき）から続ける
- 中断: `transition`（kind=suspend）→ `run_end`（suspended）。再開すると `transition`（kind=resume）→ `stage_start`（同じ訪問）から続ける
- 運用者の選択が条件を満たさない場合: `warning` → `escalation`（decision=null）→ `run_end`（awaiting\_operator）
- 警告の位置: 範囲外のファイルを捨てた警告は `stage_end` の直後。carry の項目が現在の記憶に無かった警告は、その `transition`（rollback）の直後
- 一つの実行に `run_end` が複数あってよい。最後のものが実行の最終の状態

### 3.5 遷移の種類

決定論テストと E2E の被覆は、次の六種で数える（決定 追加の論点 B）。

1. next（実行の完了を含む）
2. rollback
3. max 超過による escalate
4. unknown による escalate（本体の例外と契約違反を含む）
5. 中断と再開
6. フェーズ境界を越えるロールバックと、ゲートの再評価

## 4. 実行の状態

実行は、進行中、中断（ユーザー回答待ち）、escalate 待ち（運用者の選択待ち）、完了、中止のいずれか。中断と escalate 待ちは保存して別のプロセスで再開できる。

## 5. スナップショット形式

スナップショットは、マニフェスト（JSON）と、内容アドレスのファイル置き場から成る。マニフェストの形は contract/snapshot.schema.json で定める。

- files: 範囲内の各ファイルのパスと、内容の SHA-256。ファイルの内容は置き場に SHA-256 の名前で置く
- memory: 記憶の名前と値（JSON の値）
- gates: 通過済みのフェーズの id の一覧
- annotations: 強制通過などの注記の一覧

同じ内容のスナップショットは同じマニフェストになる。マニフェストの正規形は次のとおりで、スナップショットの id はその正規形のバイト列の SHA-256（16 進小文字）とする。

- JSON で、オブジェクトのキーを Unicode の符号位置の順に並べ、区切りは `,` と `:`（空白を入れない）
- 文字列は UTF-8 のまま書く。エスケープするのは `"`、`\`、制御文字（U+0000〜U+001F）だけで、`\b` `\f` `\n` `\r` `\t` は短い形、ほかの制御文字は `\u00xx`（小文字の 16 進）
- 数は ECMAScript の Number::toString の書き方（RFC 8785 第3.2.2.3節）。整数値の浮動小数点数は小数点を付けない（`1.0` は `1`、`-0` は `0`）。NaN と無限大は書けない
- 末尾に改行を付けない
- テストベクトルは contract/conformance/manifests.json にある
- gates はワークフロー定義のフェーズの順、annotations は古い順

記録再生で「同一スナップショットが得られる」は、スナップショットの id の一致で判定する。

## 6. 実行記録

ランタイムは、実行ごとに出来事の列（JSON Lines）を書く。形は contract/trace.schema.json で定める。分布テスト、独立性検証、E2E の被覆、遷移行列の推定は、すべてこの記録から計算する。

## 7. インターフェース

### 7.1 ステージ本体

ステージごとに一つ。ランタイムから一回の実行の文脈を受け取り、作業領域と記憶を変える。

文脈が提供するもの:

- ステージの id と、この実行での訪問の回数
- 作業領域のパス
- memory\_in に宣言した記憶の読み出しと、memory\_out に宣言した記憶の書き込み
- 種: 実行の種、ステージの id、訪問の回数から決定論的に導いた整数。確率的な偽のステージ本体はこれだけを乱数の源にする
- ユーザー入出力（awaits\_user を宣言したステージだけ）
- LLM クライアント（recorder を経由したもの）

### 7.2 指標レジストリ（決定 #2）

- names(): 実装している指標名の一覧。整合性検査器は、ワークフロー定義が参照する指標がすべてここにあることを検査する
- measure(name, view, args) → 値: view は読み取り専用のスナップショット。ステージの指標ならそのステージの終了時、フェーズの指標ならフェーズの最終ステージの終了時のスナップショット全体（範囲内の全ファイルと記憶）。view.baseline() は比べる基準のスナップショットで、ステージの指標ならそのステージの開始時、フェーズの指標ならフェーズの最初のステージの直近の開始時。変更されたパスの範囲のような、前後を比べる指標に使うargs はワークフロー定義の args。値は真偽値か数。測定できなければ失敗を知らせる

### 7.3 ユーザー入出力（決定 #4）

- ask(question) → answer: 質問（文と、任意の選択肢）を渡し、回答の文を受け取る。回答がまだ無いことを知らせてもよい（3.3）

テストではユーザーシミュレータを束縛する。

### 7.4 LLM クライアント

- complete(request) → response: request と response は JSON で表せる値。中身の形はハーネスが決める

ステージ本体の LLM 呼び出しは、必ず recorder を経由する（第9節）。フレームワーク自身のテストは LLM を呼ばない。

### 7.5 分類器

- classify(state, options) → (選んだ選択肢の id か「答え無し」, 確信度 0〜1)

options は 2.2 の選択肢（id と記述）。後ろ側（LLM や専用の分類器）は特定しない。分類器はハーネスがランタイムを組み立てる時に束縛する。決定論的なテストでは、フレームワークが用意する偽の分類器を束縛する。

### 7.6 運用者

- decide(escalation) → 選択: escalation は理由（max\_exceeded / unknown / stage\_error / contract\_violation）、ステージ、評価の結果、辺と回数。選択は 3.4 の四つ。選択がまだ無いことを知らせてもよい

運用者もハーネスがランタイムを組み立てる時に束縛する。テストでは台本どおりに選ぶ偽の運用者を束縛する。

## 8. ランタイムが実行時に強制すること

整合性検査器が静的に保証した性質を、実行時にも守る。

- 本体は、範囲内のパスのうち自分の writes にあるものだけを変える。作業領域に記号リンクを置かない（作業領域の外を指しうるので、範囲の内外を問わず契約違反）
- 本体は、memory\_out にある記憶だけを書き、memory\_in にある記憶だけを読む
- awaits\_user を宣言しないステージはユーザー入出力を使えない
- rollback の戻り先はそのステージ自身か前方、回数は max まで、carry は宣言どおり（ワークフロー定義から導くので、ランタイムが遷移を発明しない）

違反は unknown として escalate し（理由 contract\_violation）、実行記録に残す。

## 9. 記録再生

recorder は、外部から入ってくる値をすべて記録し、再生できるようにする。再開の時に受け取る回答と選択も記録する。対象は LLM の応答、ユーザーの回答、運用者の選択、分類器の結果、指標の値。記録の鍵は、実行の種、ステージ、訪問の回数、その訪問の中での呼び出しの順番、要求の内容のハッシュ。再生では外部を呼ばず、記録から返す。記録に無い呼び出しは、再生の失敗として止める（黙って外部を呼ばない）。本体がその失敗を握りつぶしても、ランタイムは再生の失敗として止める。記録と同じ種と入力で再生した実行は、同じスナップショット（マニフェスト）の列と同じ実行記録を生む。

## 10. 契約適合テスト

契約適合テスト（F2）は、ランタイムの実装が契約を満たすかを判定する唯一の手段（plan.md 第5.8節）。言語に依存しない形にするため、シナリオ（ワークフロー定義、偽のステージ本体の振る舞いの台本、偽の分類器・運用者・ユーザーの台本）と、期待する実行記録の要約、訪問ごとの開始時スナップショット（ファイルの内容、記憶、ゲート）、評価の選択肢の組で書く（contract/conformance/README.md）。参照ランタイムと、ハーネスが自前で用意したランタイムの両方が通す。
